Does the starting design change what the agent builds?

Goal. Does the way an agent first designs a program matter for later changes? We compare three starting designs on SlopCodeBench tasks:

  • Default: no design guidance in the prompt. In these runs the agent always wrote a single file.
  • Modular: told to split the program into well-organised modules.
  • Information hiding (Parnas): told to build each module around one design decision that is likely to change, hidden behind an interface.

The instruction is given only at the first checkpoint. Every later feature is added by a fresh agent session that sees only the code, not the instruction.

Questions.

  1. Do the three instructions produce differently structured code?
  2. Is the code easier to extend later? That is, do later checkpoints pass more tests, break fewer earlier tests, or cost less?
  3. Does information hiding do better than generic modularity?

This is a pilot: one run per condition per task, to see whether a difference shows up at all before running more seeds.

Key findings (one run per condition per task)

  • The starting design changes the structure: one file (Default) vs 12–57 modules (Modular, Parnas), with mean function complexity about a quarter to a half lower.
  • That structure did not make later changes cheaper or more correct. Final scores were within 3 tests of each other in every task. Modular and Parnas took 20–39% more steps, and cost 12–29% more in 3 of 4 tasks.
  • The likely reason: the agent re-reads almost all the code at every checkpoint. At about 1,000–10,000 lines it can read everything, so modules give it nothing to skip.
  • Almost no failures came from structure: 2 of 395 failing tests, in one Parnas run.

How the runs were done

Why a fresh start. To isolate the effect of code structure, each checkpoint started in a fresh session with only the code carried over; agent-written notes and documents were removed. This is stricter than normal use, where notes persist.

  • Harness. The SlopCodeBench harness, driving Claude Code (v2.1.310) with Claude Opus 5.5, thinking set to high, a 300-step cap per checkpoint, and permissions bypassed inside the container.
  • Docker. The agent worked in a Python 3.12 container on an internal network. Its only way out was a proxy that allowed the Anthropic API and PyPI. Web search and web fetch were disabled, no MCP servers were loaded, and non-essential traffic was turned off.
  • Only checkpoint 1 differs. The starting-design text (none, modular, or information hiding) appears only in the first prompt. Every later checkpoint gets the same text in all three conditions: the new spec plus "keep using the same virtual environment". So checkpoints 2 onward are built on whatever the agent made at checkpoint 1.
  • Fresh start at each checkpoint, own code kept. Before each new checkpoint the harness threw away the container and started a new one, and cleared Claude's home directory (no conversation, memory or history carried over). The workspace (the agent's code, its virtual environment and requirements.txt) was kept. Markdown files the agent wrote (for example c3's DESIGN.md in recli) were deleted, so the agent could rely only on the code itself.
  • Hidden tests. After each checkpoint the benchmark's tests ran in a separate environment against a snapshot of the code. The agent never saw the tests or the results, and the tests were not changed. Tests from earlier checkpoints run again at every later checkpoint, so one early miss is counted several times. The page calls each of these counts a failed test instance: a test that fails at 4 checkpoints counts as 4 instances.
  • Checks per cell. Every checkpoint was checked for an identical set of 17 built-in skills, no account skills, no MCP, zero skill or MCP calls, and no mention of the test or solution folders in the trace. All 12 cells passed.

What the agents did: navigation, search, implementation, testing

Read from the step-by-step traces of all 12 cells. One reviewer per task read the three conditions side by side; a sample of claims was checked against the code and the test logs. One run per condition: these describe what happened in these runs, not effects of the prompts. Full reports: features/scbench/analysis/qual/.

Same in every condition

  • Navigation. Each checkpoint opened with ls/find, then dumping most of the code with cat or sed. With modules (c2, c3) that meant reading nearly every module again; c1 read slices of its one file.
  • Search. Done through shell commands. No run used the Grep or Glob tools or read its own docs.
  • Editing. Mostly Python find-and-replace scripts or whole-file rewrites run in the shell, rarely the Edit tool.
  • Steps before the first edit were similar across conditions, with no consistent ordering.
  • Finishing. Every checkpoint ended with the agent saying the spec was done, but some hidden tests still failed.
  • The starting design was never mentioned again after checkpoint 1.

Different by condition

  • Shape. c1 kept one growing file in every task (sith ~6,700 lines). c2 built a package. c3 built a package whose module docstrings each name a "Secret:".
  • Spread of edits. c2 and c3 touched many files per feature (recli checkpoints 2–8: 4 / 29 / 34 files edited); c1 re-read and patched its one file.
  • Hub files. Even in packages one or two files grew every checkpoint (recli c2 upgrade.py 875 lines; c3 catalog.py, and messages.py holding every message).
  • Own tests. c1 never wrote a test suite. c2 and c3 did in sith and recli (recli ends with 208 and 217 own tests). In eve_industry and metric_transform_lang no condition wrote unit tests.
  • Module boundaries. In metric_transform_lang c2 called another module's private function; c3 added public helpers instead.

Struggles and weaknesses

  • Failures trace to spec readings, not structure. No failure in any task was traced to duplicated logic or a bypassed interface.
  • One early miss repeats. A misread at checkpoint 2 is counted again at every later checkpoint, which drives most gaps between conditions.
  • Own tests confirmed own readings. c2's sith tests asserted the wrong name NoneType; in recli c2 and c3 saw the breaking first-run message in their own tests and changed the tests, not the program.
  • Explaining evidence away. eve_industry c1 found the ships its relic rule missed and called them "invented from Tech I blueprints".
  • Abandoned checks. eve_industry c2 tried to test the 100% clamp, the probe broke, and it moved on.

Isolation and leakage checks

Every one of the 12 cells passed check_cell.py at every checkpoint. The checks were:

  • an identical 17-skill list at every checkpoint, with no anthropic-skills, no MCP servers or tools, and 0 Skill or MCP calls;
  • 0 mentions of .evaluation_tests, scb-problems or solutions/ in any agent transcript;
  • a fresh container at every checkpoint after the first, with an identical starting listing;
  • agent-written docs (.md/.rst) deleted before the next checkpoint;
  • 0 credential files and 0 token-shaped strings in the run directory;
  • the harness verifier (verify_setup.sh) reporting ALL PASS before each cell;
  • every transcript fully parsed. In recli c3 checkpoint 8 the log writer dropped a newline at the 4,096-byte mark, so two complete records share one line. The checker now reads both and fails a cell on any unreadable fragment instead of skipping it. All 12 cells re-checked with 0 unreadable fragments.

The reference solution passes 100% of tests at every checkpoint of all four tasks. For recli, a split copy of the reference (entry file plus a package) also passes 100% at checkpoints 1 and 8, so multi-file solutions are not penalised by how the tests load the program. One exception: metric_transform_lang checkpoint 4 skips 46 checkpoint-1 tests by design, and those count as non-passes for every condition alike.
